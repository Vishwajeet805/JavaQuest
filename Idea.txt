Haan — ab JavaQuest ko **“Week 1 MVP” se “production-capable learning platform”** ke perspective se design karna chahiye. Maine tumhari master documentation ko baseline rakha hai: JavaQuest ka goal tutorial website banana nahi, balki structured lessons + coding + assessment + mistake analysis + revision + mastery system banana hai.  Aur tumhari existing spec ka ye principle bilkul sahi hai ki arbitrary learner code main application server par directly execute nahi hona chahiye. 

Research ke baad main **ek important architecture decision change/strengthen** karunga: abhi Judge0 ko permanently lock nahi karna chahiye. Judge0 strong option hai, lekin GPL-3.0 licensed hai; Piston MIT licensed hai aur self-host ho sakta hai; aur long-term JavaQuest ko apna abstraction layer rakhna chahiye taaki execution engine swap kar sake. ([GitHub][1])

# JavaQuest — Full Development Blueprint

## 1. Final architectural philosophy

JavaQuest V1 ko is tarah banana chahiye:

```text
                    ┌───────────────────────┐
                    │      Web Client       │
                    │ React + TypeScript    │
                    │ Monaco Editor         │
                    └───────────┬───────────┘
                                │
                           HTTPS / API
                                │
                    ┌───────────▼───────────┐
                    │   JavaQuest Backend   │
                    │   NestJS + TS         │
                    │                       │
                    │ Auth                  │
                    │ Learning Engine       │
                    │ Question Engine       │
                    │ Assessment Engine     │
                    │ Progress Engine       │
                    │ Mastery Engine        │
                    │ Revision Engine       │
                    │ Gamification          │
                    └──────┬────────┬───────┘
                           │        │
                  PostgreSQL      Redis
                           │        │
                           │   Execution Queue
                           │        │
                           │        ▼
                           │  ┌──────────────┐
                           │  │ Runner Worker│
                           │  └──────┬───────┘
                           │         │
                           │   CodeRunner Adapter
                           │         │
                           │    ┌────▼────┐
                           │    │ Sandbox │
                           │    └────┬────┘
                           │         │
                           │    Java compile/run
                           │
                    Analytics / Logs
```

Sabse important architectural decision:

> **Core product = modular monolith. Code execution = separate trust boundary.**

Microservices tab tak nahi.

Tumhari existing documentation already Users/Auth, Learning Engine, Assessment Engine aur Code Execution Service ko logically separate karti hai.

# 7. Runner abstraction

Core backend ko Piston/Judge0 ka naam bhi ideally nahi pata hona chahiye.

```ts
interface CodeRunner {
  execute(
    request: ExecutionRequest
  ): Promise<ExecutionResult>;
}
```

Implementations:

```text
PistonRunner
Judge0Runner
FutureJavaRunner
```

JavaQuest sirf ye bole:

```text
runner.execute(...)
```

Iska enormous long-term benefit hai.

# 8. Judge0 vs Piston vs custom runner

Research ke baad meri ranking thodi nuanced hai.

### Judge0

Pros:

```text
mature
sandboxed
resource controls
execution API
education use cases
multi-language
```

Judge0 CPU, wall-time, memory, stack aur process/thread limits expose karta hai. ([GitHub][5])

Single aur multi-file submissions bhi support karta hai. ([GitHub][6])

Lekin:

> Judge0 CE **GPL-3.0** licensed hai. ([GitHub][1])

Isliye commercial deployment se pehle licensing implications review karna chahiye.

---

### Piston

Piston architecture bhi strong hai.

It uses Isolate, Linux namespaces, unprivileged users and cgroups. Networking disabled by default hai; runtime, memory, processes, files aur stdout limits bhi available hain. ([GitHub][7])

Piston package MIT licensed hai. ([GitHub][8])

Public API par depend nahi karna chahiye: February 15, 2026 se free public access restricted ho gaya hai. ([GitHub][9])

Self-host okay.

### V1 research preference

Main ab ye recommend karunga:

```text
Prototype both:

Piston self-hosted
vs
Judge0 self-hosted
```

5–10 real Java workloads run karo.

Compare:

```text
startup
latency
Java Scanner input
compile errors
timeouts
memory handling
multiple classes
concurrency
deployment difficulty
maintenance
license
```

Then lock one.

**CodeRunner Adapter ki wajah se choice irreversible nahi hogi.**

# 9. Custom sandbox abhi mat banana

Bahut tempting hoga:

```text
Docker run java...
```

But mat karna.

gVisor khud explicitly warn karta hai ki ordinary containers untrusted code ke liye sufficient sandbox nahi maane jaane chahiye. ([GitHub][10])

gVisor untrusted workloads ke liye additional isolation provide karta hai by inserting an application-kernel layer between workload and host kernel. ([gVisor][11])

Future architecture ho sakta hai:

```text
Custom Runner
     ↓
containerd
     ↓
gVisor / runsc
     ↓
Java container
```

Lekin ye **Phase 3/4 infrastructure work** hai.

Week 1 product ka nahi.

# 39. One correction to our earlier decision

Earlier humne kaha tha:

> “Self-hosted Judge0 lock kar dete hain.”

Research ke baad main ise slightly revise karunga.

**Lock Judge0 nahi. Lock `CodeRunner` architecture.**

Then benchmark:

```text
Judge0
vs
Piston
```

Judge0 excellent hai, but GPL-3.0 licensing factor hai. ([GitHub][1]) Piston MIT hai, self-hosting allowed hai, aur its sandbox uses namespaces/cgroups/Isolate with multiple resource limits. ([GitHub][8])

This is much safer product engineering.
